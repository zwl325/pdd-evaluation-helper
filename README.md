# PDD 评价自动回复与举报助手

版本：**2026-10-14.2**。脚本名称为 **PDD评价筛选助手 v2026-10-14.2**。名称中的版本随发布同步生成；`@namespace`、安装文件名及更新地址保持固定。

UI/UX 与生命周期管理的后续计划见 [TODO.md](TODO.md)；本次严重 bug 与隐患检查见 [REVIEW-NOTES.md](REVIEW-NOTES.md)，其中两项 P1 风险仍待处理。

公开仓库：[zwl325/pdd-evaluation-helper](https://github.com/zwl325/pdd-evaluation-helper)。

**[安装 / 更新 Tampermonkey 脚本](https://raw.githubusercontent.com/zwl325/pdd-evaluation-helper/main/pdd-evaluation-filter.user.js)**

脚本在已登录的商家后台内操作DOM，无需CDP连接。面板在`https://mms.pinduoduo.com/*`的各个后台页面显示，支持“自动筛选回复”和“自动举报差评”切换。两种模式分别保留数量、商品ID、文案、批次台账和状态；仅显示当前模式的业务区。点击“一键运行”时，已在评价路径直接操作，其他页面才在当前标签页进入指定评价页。普通页面加载不启动批次；主动跳转产生的一次性任务会在目标页继续。

脚本适配不同PDD店铺；无需填写或修改店铺名，也不要求出现特定子账号或退出文字。可读店铺名称仅作本机台账备注，读不到则留空，执行依据为当前页面的评价记录。

## 使用

1. 在启用了Tampermonkey的浏览器打开安装链接并安装。若浏览器显示源代码，可复制全部代码到Tampermonkey新脚本中保存。
2. 保持当前商家登录状态，打开拼多多商家后台任意页面，例如首页、商品管理页或订单页；无需手动进入商品评价页。
3. 在右下角面板选择模式。回复模式填写“检查数量 N”，举报模式填写“举报数量（本次成功数量）”；两种模式的商品ID和数量均可留空，切换保留各自输入。运行期间禁止切换及修改参数。
4. 点击 **“一键运行”**。如果当前路径为`/goods/evaluation/index`（兼容末尾斜杠及不同查询参数），直接处理，保留当前URL和页面日期条件。其他页面在同标签页进入：
   `https://mms.pinduoduo.com/goods/evaluation/index?msfrom=mms_sidenav`，保留本次N和商品ID参数后继续。
5. 观察运行提示，或点击 **“检查状态”** 立即读取当前状态。该按钮在运行期间仍可用，只读状态，不触发筛选、查询或回复，也不会覆盖当前进度。
6. 可点击 **“导出本机台账”** 下载当前模式的批次及提交记录JSON；展开 **“查看统一回复文案”** 或 **“查看统一举报文案”** 可查看脚本实际使用的完整文案。这两个入口也只读取内容。
7. 需要中止时，点击“一键运行”正下方的 **“急停”**。按钮始终可点击，立即中断当前等待和后续动作；跳转期间会清除待执行任务，目标页加载后不继续。已填但未提交的草稿保留，请人工检查弹框；已提交的回复无法撤销，结果未确认时保留待核验台账。
8. 标题栏 **“收起”** 折叠整个内容区，再点“展开”恢复；**“最小化”** 变为紧凑小窗，点击“恢复”展开。拖动标题文字或最小化小窗的文字区域可以移动面板。位置、显示状态和模式保存在当前浏览器，同一后台域名刷新或跳转后保留；恢复和调整窗口大小时限制在可视范围。收起和最小化均保留当前模式的运行状态、计数及可用的急停按钮，任务继续执行。

| 参数 | 填写时 | 留空时 |
| --- | --- | --- |
| 检查数量 N | 按当前列表顺序检查不同身份的记录，达到N立即结束；N仍是检查数量 | 遍历当前查询结果直到没有尚未检查的记录 |
| 举报数量 | 本次成功举报目标1～30；跳过或未确认提交不计入成功数，自动限制到今日剩余额度 | 使用今日剩余额度作为成功举报目标；结果不足时正常结束 |
| 商品 ID | 仅填写指定的完整数字ID | 清空页面残留商品ID，不沿用旧值 |

状态区持续显示筛选是否就绪、批次阶段、已检查数、确认回复数、跳过数和停止原因；有未确认提交时另行提示待核验数量。读取一条新的评价身份时检查数加1，成功证据确认后回复数加1；未确认提交不算成功回复。

业务区保留一键运行、急停、检查状态、导出本机台账和文案展开入口；N和商品ID仍为可选输入。标题栏新增收起和最小化，紧凑状态另有恢复入口与急停。没有重新加入三个独立筛选按钮或星级徽标。所有急停按钮与本页取消API共用同一入口，只终止后续动作。发出提交后取消、超时或失去页面状态，会留下未知提交台账，阻止自动重发。急停不会强制终止浏览器已经发出的导航；导航完成前源页面仍禁止再次启动。

## 自动举报差评

举报数量是**本次成功提交的目标**，与回复模式的检查数量不同。例如填2，前面5条都不符合也会继续检查；确认成功2条后立即停止。平台已接收举报不表示已认定该评价为恶意。

1. 进入评价页，清除4星、5星及回复状态限制，保留页面已有日期条件。商品ID仅使用本次指定值，留空时清除残留ID；订单或关键词残留时停止。
2. 按 **1星→2星→3星** 依次选择并查询。当前星级所有页面检查完，且本次成功目标和日限额都未达到，才进入下一星级；3星处理完停止。
3. 每次读取当前页尚未检查的身份，只处理正文**完全等于**`该用户未填写文字评价`的记录。空白、换行、标点或附加文字均不匹配。页面已举报状态或本机历史确认举报跳过，不计本次成功数。
4. 当前记录星级须等于当前查询星级；在对应记录内点击“举报”，等待唯一“举报该评价”弹框的原正文、星级和表单状态稳定，再继续。加载过程中暂时缺少正文或评分时等待，持续不匹配或评分无法确认时停止。
5. 选择“同行恶意差评”，等待说明框，完整填写下方文案；核对原生`input`/`change`输入结果、20～500字限制、选中状态和`reason_type=8`。
6. 提交前保存一次尝试到本机台账，仅点击一次“提交举报”。本次新出现的精确“举报成功”提示与弹框关闭同时满足，才确认成功并将本次计数加1。
7. 当前页没有新记录时自动翻页；成功后如列表收缩，返回前页重新扫描，通过订单号、商品ID和评价时间去重。达到成功目标或当天30条上限立即结束。

**每日额度按北京时间日期统计，覆盖同一浏览器配置文件、同一商家后台origin的脚本提交记录，跨标签页、刷新及店铺备注变化不重置。** 不依赖任何固定店铺。不同浏览器、设备以及人工提交无法由此本机台账自动统计；清除站点数据也会丢失历史。

提交前的`submitting`和提交结果不明的`submitted_unverified`暂占额度，但不算成功数。任意日期存在未知举报时，新举报批次停止，需核验后继续；不能只凭弹框关闭、记录消失或超时记成功。运行跨北京时间日期时停止，重新运行才使用新日额度。状态区显示今日成功、待核验、剩余额度、本次目标、当前星级、检查数、成功数、跳过数和停止原因。

用户提供的DOM包含举报弹框和输入元素，**尚未包含实际提交成功／失败提示或已举报状态样本**。当前成功文字及已举报状态为兼容定位，已通过合成页面测试，未在真实后台验证；如实际提示不同，脚本会保留未知提交并停止。后续应补充成功提示的`outerHTML`、selector和出现／消失方式。页面级提示还存在与评价身份不能直接关联的证据边界，见`REVIEW-NOTES.md`。

### 星级核验与错误诊断

2026-10-14.1以弹框中可见的`star_filled` SVG数量读取评分，固定5个图标但仅部分高亮时可能误判。2026-10-14.2删除该计数方式：读取评分控件的明确数值（如存在`aria-valuenow`、`data-score`）、满星状态类，以及实际绘制颜色。灰色图标不计为高亮星；同一个星位的背景层与高亮层去重，被零宽裁切隐藏的层不计入评分。当前颜色辅助识别覆盖PDD给定样本的红色／灰色，未知绘制方式、半星、非法数值或相互冲突的证据都会停止，不能据预期星级反推实际值。

弹框加载和选择原因后的重绘先等待匹配内容连续稳定300ms，默认最多等待6秒；稳定窗口也在内容、星级或读取依据变化时重置。正文保持全文严格相等，尾部空白／换行不放宽。填写后和提交前重新核验，真实不匹配仍阻止提交。

遇到弹框核验错误，导出的`batch.error.details`与对应记录的`reportDiagnostics`保存以下本机诊断字段：

| 字段 | 含义 |
| --- | --- |
| `stage` | `opened`、`reason_selected`、`text_filled`、`before_submit`等读取阶段 |
| `expectedContent` / `actualContent` | 列表原文与弹框实际原文；不裁剪空白，不做归一化 |
| `expectedStar` / `actualStar` | 预期星级与实际读取值；无法确认时实际值为`null` |
| `modalCount` / `modalTitle` / `detailCount` | 可见弹框数量、标题及正文元素数量 |
| `rating` | 评分来源、无法读取的原因、SVG数量、可见图标数量、原始数值、状态类、图标绘制颜色及裁切比例 |

正文不符报`REPORT_MODAL_CONTENT_MISMATCH`，星级不符报`REPORT_MODAL_STAR_MISMATCH`，评分不明报`REPORT_MODAL_STAR_UNREADABLE`，正文一直未加载报`REPORT_MODAL_NOT_READY`。错误信息分开描述原因，字段允许核对多个同时不符的实际值。这些数据只保存到本机台账，不上传到仓库。

此前用户台账只能确定弹框核验失败、尚未提交，未保存现场实际正文／评分；本轮修复针对已离线复现的SVG误计及加载时序路径，不能据此认定该台账的现场原因已经证实。新的诊断字段用于后续实际页面核对。

统一举报文案：

```text
平台审核组：
近期店铺出现多个异常评价，经数据核查，存在以下可疑特征：

1. 账号共性：头像简单或使用随机数字 ID。
2. 行为异常：均直接购买，平均停留不足5分钟。
3. 评价异常：差评均反映商品质量差。
4. 物流正常：每24小时有物流更新，仍投诉物流慢。
5. 关联特征：每逢大促集中出现中差评，请明察，还店铺清白。
6. 我愿意退换货，但该同行拒绝，并以差评要挟，谋取不正当利益，影响公平竞争，请严查！
```

举报台账与回复台账使用不同键，导出包含本次举报批次、每日额度和完整尝试历史，不覆盖回复历史。未知举报的人工核验接口是异步接口，并持有与批次相同的跨标签页运行锁：

```javascript
window.PDDEvaluationHelper.readReportJournal(); // 从attempts复制id
await window.PDDEvaluationHelper.resolveReportSubmission(
  '从台账复制的attempt id', 'confirmed', '填写平台记录等人工核验依据'
);
// 仅人工核实没有提交时释放额度，旧尝试及依据保留；重新运行另建attempt。
await window.PDDEvaluationHelper.resolveReportSubmission(
  '从台账复制的attempt id', 'not_submitted_user_verified', '填写未提交的核验依据'
);
```

核验只修正本机提交历史与额度，不会启动举报，也不会回写过去批次的自动成功计数。

## 自动回复批次流程

1. 点击“一键运行”后，评价路径直接处理，其他后台页同标签页进入指定评价页并保留本次参数；不读取或绑定启动页店铺。
2. 等待评价容器、筛选区域、查询表单和结果表加载；店铺名称只作可选台账备注，不参与运行校验。
3. 依次选择4星、5星、未回复；已选项跳过，不反复切换。
4. 填写指定商品ID，或清空残留商品ID。若订单号、关键词等其他可编辑输入仍有残留值，停止并提示清空。
5. 点击“查询”。必须观察到结果区域变化或加载活动，再等待正文、页码和总数持续稳定800ms。空结果可正常结束；没有完成证据时不会使用旧列表。
6. 从查询第一页读取第一个尚未检查的评价身份，检查数加1并保存台账。不跨页预采集，不冻结原始前缀。逐条读取当前正文；不符合则跳过，符合则立即打开该记录内的“回复/互动”。遇到该身份的历史未知提交时停止，前面已经确认的回复保留。
7. 打开弹框和提交前只在当前页重新核对订单号、商品ID、评价时间和原文，避免将已变化的记录当作原评价。已检查身份在本批次中只计一次；历史已确认回复跳过发送。
8. 在唯一“快捷回复”弹框内通过原生输入setter及`input`、`change`事件填写统一文案。核对精确输入值、可用按钮、查询条件和评价身份。
9. 在本机台账写入`submitting`后只点击一次“回复”。收到本次新成功提示且弹框关闭，或对应身份下出现完整回复正文，才保存`confirmed`。
10. 继续读取当前列表尚未检查的记录，当前页没有新记录时翻页；回复后列表可能收缩，必要时从第一页重新扫描，防止后页记录前移造成漏查。通过已检查身份去重，不寻找某个固定历史记录。达到N或遍历完毕后结束，显示检查数、确认回复数和跳过数。

已在评价页时沿用当前日期条件；从其他后台页跳转时沿用目标页加载后的条件，并记录在本批筛选快照中。没有迁移交接文件里的固定历史日期、前5/28条、每页40条、历史店铺名或登录退出流程。

## 范围、翻页和正文规则

**N不是回复配额。** 例如N=5，其中只有1条符合模板，则检查5条、回复1条，其他4条跳过；不会为了凑够5次回复继续找后面的记录。

检查和去重的每条身份包含：

```text
订单号 + 商品ID + 评价时间
```

台账仍保存可选`shop`备注，备注留空、改名或页头变化不会改变记录身份。本版不再以店铺名称变化判断是否停止，页面地址、查询条件、评价身份和完整正文的变化仍按原规则核验。

本版使用即时列表和计数器，不再保证检查对象是查询瞬间冻结的前N条。回复、外部操作或新增评价导致列表重排时，继续选择当前列表尚未检查的身份，检查达到N便结束。仍会在提交前核对当前记录的身份及原文，变化则停止。旧台账的`skipped_missing_locked_record`状态保留，本版不再通过跨页找回生成此状态。

未指定N时，逐条回复和翻页，回复后重新扫描前页并去重，直到当前结果没有尚未检查的身份。运行中新增且符合当前查询的记录可能被检查；这与旧版冻结全量结果不同。累计翻页超过10000次会停止，避免无限循环。

只允许正文全文符合：

```regex
^该用户觉得商品很好(?:，给出了[45]星好评)?$
```

允许“该用户觉得商品很好”、以及原有完整4星/5星默认好评三种正文。不使用`trim()`放宽匹配，不接受尾部空白、末尾换行、附加内容、其他手写好评或“商品较好”。JavaScript正则的`$`可以匹配最终换行之前，因此实现还要求匹配结果覆盖整段正文。

统一回复使用本次用户提供的原文，没有沿用交接文件中的额外空格：

> 小店每天最开心的事莫过于看到亲的好评，亲的好评就像是清泉一样滋润我们的心田，小店会更加的珍惜亲的好评，不断的改进自己，完善自己，力求让小店的服务做得更好，店铺做得更大，也是为了让亲能够更好的买到自己的喜欢的宝贝。你的好评就是对我们最大的肯定和鼓励，希望亲再次关顾我们的店铺，检验小店的进步。

## 本机台账和提交恢复

本批已检查记录、计数与逐条结果保存在当前标签页的`sessionStorage`；提交状态另外保存在该商家后台origin的`localStorage`。后者供刷新和其他同源标签页读取，已经确认的身份会跳过发送。未知提交按订单号、商品ID、评价时间匹配：逐条遇到该身份时停止，保留前面已经成功的回复；其他店铺或其他订单的未知台账不会按店铺名封锁当前批次。批次还使用Web Locks避免脚本在多个同源标签页中同时提交。

兼容读取旧版含店铺名的四字段key，按旧条目的订单号、商品ID、评价时间继续去重和核验。旧条目、成功证据及人工核验历史保留，无需清空台账，也不会因去掉店铺校验而自动重发旧记录。

台账不会上传到GitHub或外部服务器。可点击面板“导出本机台账”，也可在控制台调用`window.PDDEvaluationHelper.exportLedger()`下载JSON，其中包含店铺、订单号、商品ID和评价时间等业务数据，需自行保管。它属于当前浏览器的本地记录，不能替代服务器查询，也不是跨浏览器、跨设备的完整去重库。

| 记录状态 | 含义 |
| --- | --- |
| `pending` | 已读取当前身份，尚未完成检查或回复 |
| `confirmed` | 已收到本次明确成功证据 |
| `skipped_non_template` | 全文不符合模板 |
| `skipped_missing_locked_record` | 旧版找不到锁定身份的历史状态；本版不新增 |
| `skipped_previously_confirmed` | 本机已有该身份的确认提交 |
| `submitting` | 提交前已落盘；若页面意外关闭，结果仍须核验 |
| `submitted_unverified` | 提交已发出，未能确认结果；立即停止 |

未知结果不会因为弹框消失、记录消失或列表缩减而自动判定成功，也不会自动重试。人工核验前，先确保其他同源标签页的脚本任务均已停止；当前人工核验接口还没有持有跨标签页运行锁（详见 `REVIEW-NOTES.md`）。先人工查看该身份对应的实际回复状态，再调用明确的人工核验接口解除阻塞：

```javascript
// 先读台账，取得完整key；key不是列表序号。
window.PDDEvaluationHelper.readSubmissionJournal();

// 人工确认为已回复：
window.PDDEvaluationHelper.resolveSubmission(
  '从台账复制的完整key',
  'confirmed',
  '填写人工核验依据'
);

// 人工确认为未回复：
window.PDDEvaluationHelper.resolveSubmission(
  '从台账复制的完整key',
  'not_replied_user_verified',
  '填写人工核验依据'
);
```

核验结论保留在提交历史中，接口本身不提交回复。确认为未回复后不会自动启动；重新启动批次时按新的查询、即时列表和检查数量处理。

## 模块与定位维护

为方便Tampermonkey安装，交付仍为一个`.user.js`文件；内部按职责隔离：

| 模块 | 职责 |
| --- | --- |
| `Config` | DOM选择器、正文规则、回复文案、版本和等待配置 |
| `DOM` / `Wait` | 基础可见性、筛选定位、超时和取消 |
| `Actions` | 独立筛选和批次共用的执行锁、状态通知 |
| `ReviewDOM` | 查询输入、评价身份、页码、弹框、结果证据及可选店铺备注 |
| `Ledger` | 批次快照、提交前落盘、历史状态和人工核验 |
| `Results` | 查询完成、稳定判据、翻页和当前页未检查身份读取 |
| `Replies` | 精确填文、单次提交、明确成功证据、未知结果停止 |
| `Rating` | 评分值、满星状态、实际绘制颜色、裁切层及读取诊断 |
| `ReportDOM` | 举报星级、记录核对、原因选择和举报弹框定位 |
| `ReportLedger` | 举报独立台账、北京时间日额度和持锁人工核验 |
| `Reports` / `ReportWorkflow` | 单次举报提交、成功确认、按星级遍历和成功目标 |
| `Workflow` | 参数、页面跳转、跨标签页锁和完整批次流程 |
| `Panel` / `App` | 操作界面、折叠/最小化/拖动、导航和页面生命周期 |

定位依据为用户提供的《Tampermonkey-点击动作DOM定位清单.md》、交接文件中的历史DOM信息及2026-10-14的《定位元素.txt》。公开仓库只保存选择器和合成夹具，不上传原始DOM文件中的业务数据。与已有定位不同的地方主要是：

- 分页增加上一页`beast-core-pagination-prev`，用`PGT_pagerItemActive`读取实际页码，用`PGT_totalText`读取总数。
- “回复/互动”兼容半角`/`与全角`／`，仍限制在对应身份分组内。
- 去除强制店铺识别和店铺名称一致性校验；历史页头结构仅用于尝试读取台账备注，缺失或不唯一时留空。
- 成功提示同时观察节点添加和文本变化，清除上一条提示后再开始本次提交。
- 举报入口限定在记录分组中的`[data-tracking-click-viewid="report"] a`；弹框以标题、正文和星级复核。原因通过`#reportType`与`bad_peer_reviews`定位，说明框用`#describesNegativeReview`，提交按钮用`new_confirm_report_btn`，避免使用页面序号和长`nth-child`链。

无唯一目标、评价身份不完整、查询条件变更、意外互动详情、已有回复草稿、输入未被组件接受或持久化失败，都停止操作。

真实页面DOM变化后，优先调整`Config.selectors`或`ReviewDOM`相应函数；不能通过取第一个目标、全页按钮序号或放宽正文匹配规避核验。

## 本页API

```javascript
window.PDDEvaluationHelper.readState();       // 原有筛选状态
await window.PDDEvaluationHelper.select('4星');
await window.PDDEvaluationHelper.selectAll();

// 与面板“一键运行”相同：评价页直接执行，其他后台页跳转后执行一次。
await window.PDDEvaluationHelper.oneClickRun({ n: 5, goodsId: '123456789012' });

// 保留的兼容入口，导航判断与oneClickRun一致。
await window.PDDEvaluationHelper.startBatch({ n: 5, goodsId: '123456789012' });
await window.PDDEvaluationHelper.startBatch({ n: 5 }); // 商品不限
await window.PDDEvaluationHelper.startBatch({});       // 全部查询结果

window.PDDEvaluationHelper.readBatch();
window.PDDEvaluationHelper.readSubmissionJournal();
window.PDDEvaluationHelper.exportLedger();
window.PDDEvaluationHelper.cancel();          // 与急停按钮相同，同步返回是否取消了执行/待执行任务

// 举报n是本次成功目标，留空使用今日剩余额度；同一评价页直接执行。
await window.PDDEvaluationHelper.startReportBatch({ n: 2, goodsId: '123456789012' });
await window.PDDEvaluationHelper.oneClickReportRun({ n: 2 });
window.PDDEvaluationHelper.readReportBatch();
window.PDDEvaluationHelper.readReportJournal();
window.PDDEvaluationHelper.readReportQuota();
window.PDDEvaluationHelper.exportReportLedger();
```

`oneClickRun`和`startBatch`使用`n`和`goodsId`参数；旧版`expectedShop`已移除，旧调用传入该字段也不会再绑定店铺。接口返回Promise，错误带`code`。主动启动的导航任务有效期为2分钟，只消费一次；完整的旧版导航参数也能继续，旧店铺约束不再生效。执行后再次手动刷新不会自动重跑，已进入回复阶段的批次也不会自动恢复。

## 远程自动更新

继续使用原生Tampermonkey更新源：

| 配置 | 地址 |
| --- | --- |
| `@updateURL` | [pdd-evaluation-filter.meta.js](https://raw.githubusercontent.com/zwl325/pdd-evaluation-helper/main/pdd-evaluation-filter.meta.js) |
| `@downloadURL` | [pdd-evaluation-filter.user.js](https://raw.githubusercontent.com/zwl325/pdd-evaluation-helper/main/pdd-evaluation-filter.user.js) |

检查周期由Tampermonkey设置决定。旧版2026-10-12尚无更新源，需要通过安装链接更新一次；后续已配置更新源的版本可在原脚本上执行“检查更新”，再刷新已打开的PDD后台页面，面板版本显示`2026-10-14.2`即可确认当前页面已加载本版。

本版按需求把版本加入`@name`。若手动打开安装链接后Tampermonkey提示新增另一个脚本，请先停用旧副本，或在原脚本编辑器中替换代码；确保只有一个副本启用，避免两个实例同时运行。仅保持命名空间不作为手动安装一定原位更新的保证。

## 版本管理与发布

使用日期式版本 **`YYYY-MM-DD.N`**：日期取发布当天，同一天从`.1`开始递增；例如本次为`2026-10-14.2`，当天后续发布为`.3`，次日首次发布为`2026-10-15.1`。沿用已有日期式版本序列，避免切换到较小的新版本号影响更新比较。Tampermonkey官方文档说明`@version`用于更新检查，每次更新都应递增，并给出了日期式版本示例。

`@version`是唯一版本来源。不要手动分别维护名称、运行时版本与元数据；执行升版命令后，工具同时生成：

- 主脚本的`@name`：`PDD评价筛选助手 v<版本>`。
- 主脚本的`@version`和`Config.version`。
- 用于更新检查的轻量`pdd-evaluation-filter.meta.js`。

例如下次同日发布，运行以下命令；其他日期替换成当次发布版本：

```text
node scripts/sync-metadata.cjs --version 2026-10-14.3
node scripts/sync-metadata.cjs --check
node tests/metadata.spec.cjs
node --check pdd-evaluation-filter.user.js
```

升版命令要求版本严格大于当前版本，按数字比较日期与序号（`.10`大于`.9`），拒绝同版重发、降版、非法日期、零序号和前导零。无参数的`node scripts/sync-metadata.cjs`仅按当前`@version`重新同步；`--check`只读，检测不一致时失败，不修改文件。

如果本次还修改DOM、交互或批次流程，另行运行浏览器回归：

```text
node tests/filter-helper.spec.cjs
node tests/batch-workflow.spec.cjs
node tests/report-workflow.spec.cjs
```

检查通过后更新[CHANGELOG.md](CHANGELOG.md)，使用`git`提交并推送到`main`；以同一提交创建`v<@version>`标签和GitHub Release，附上主脚本与元数据文件及发布说明。已发布标签和版本不覆盖，修正需要新版本。GitHub Actions检查语法、名称/版本/元数据一致性及10项版本工具测试；浏览器流程测试在本机运行。

## 验证边界

测试记录见`TEST-RESULTS.md`。两个HTML夹具都使用合成店铺与订单，测试拦截全部网络请求，没有访问真实PDD服务或提交真实评价。批次用例缩短结果稳定时间与失败超时以提高测试效率，生产脚本使用800ms结果稳定窗口、15秒结果/提交超时和300ms输入状态稳定窗口。

尚未在真实PDD页面验收本次完整批次。`element.click()`是合成事件，受控输入、评价列表、分页结构和成功提示仍需现场确认。店铺名称和页头结构不再是兼容前提；各店铺的实际评价DOM仍须符合本脚本定位规则。列表DOM稳定是DOM层完成证据，不等于网络事务完成保证；页面没有可读完成证据时脚本停止。
